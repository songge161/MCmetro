# MC Metro 项目章程

版本：v0.2.0 · 更新日期：2026-10-30

状态：真实街区生成原型，尚未完成游戏内验收。
本章程整合已确认的产品方向，替代旧版特定国家大地图设想。
旧文档保留于 [历史归档](../docs/archive/PROJECT_KICKOFF_v0.1.md)，其中命令、规模和里程碑不作为当前承诺。

## 1. 产品定位

MC Metro 是一个本地优先、面向 Minecraft Java 版的外部真实城市地图生成器。
用户指定现实地点，系统利用地理数据、程序规则和可选 AI 设计，生成保留道路布局、
地标关系与街区特点的可玩地图，并逐步接入模组材料和交通系统。

产品不限定国家或城市；池袋是第一个验证地点，不是产品范围。
以创造模式观光探索为主：沿街行走、进入门面、上楼参观，后续乘坐交通工具连接不同区域。
不是纯聊天规划器，也不是必须依附游戏运行的单体建筑模组。

## 2. 保真与可玩性

| 对象 | 目标 | 允许的简化 |
| --- | --- | --- |
| 道路 | 主路、路口和街区连接尽量贴近现实 | 普通街段适度缩短，宽度按可玩尺寸保留 |
| 地标 | 相对位置合理，外形与主要特征可辨认 | 次要细节、复杂内部可简化 |
| 普通建筑 | 轮廓、高低关系和街区风格协调 | 缺失数据采用明确标注的推定 |
| 门面 | 具体到单个店面，沿街连续、不突兀 | 不要求逐一复刻真实商户 |
| 室内 | 有入口、楼梯和可探索上层 | 不追求真实户型与完整装修 |
| 交通 | 最终可运行、可乘坐、可保存 | 初期只验证少量站点和线路 |

基本原则：保留真实空间关系，压缩普通间距，不压缩到门、楼梯、道路、站台无法使用。
真实数据、合理推定、程序创作必须分开记录，不把生成店面标为现实还原。
地标使用保护范围；不得为了塞入目标尺寸而静默挤占关键结构。
当前真实样板不压缩，作为后续布局对照；演示规划器的压缩原型不代表真实街区压缩已完成。

## 3. 产品形态与资源约束

- 外部生成器负责数据、规划、生成、校验、预览与导出。
- 当前在 Mac 开发和离线测试；主要使用目标是 Windows 本地生成和 Minecraft 游戏验收。
- 游戏候选基线为 Java 1.20.1 + Fabric；精确模组、加载器与 Java 版本通过测试后锁定，不暗中迁移。
- 当前交付为 `.schem` + 质量报告 + 预览 + 导入/验收说明，不直接修改玩家世界。
- 后续按需求增加辅助模组、运行时注册表读取、世界导出或桌面界面；不把规划功能宣传为已有能力。
- 本地优先：不要求服务器、全球 OSM 数据库或自建 Overpass。区域数据下载后本地裁切、缓存和反复使用。
- SSD 总预算不超过 100GB，近期正常使用目标不超过 10GB；原始数据和构建产物不进入 Git。
- 目标 Windows 硬件按用户提供的 Ryzen 9、RTX 3080 16GB、32GB DDR4 进行后续实测，不预先承诺帧率。

## 4. 生成工作流与职责边界

```text
地点 / 范围 / 保留要求
  → 区域数据获取、本地裁切与来源登记
  → 道路、建筑、地标、交通与缺失信息整理
  → 布局规划：保护可玩尺寸，按需选择性压缩
  → 道路、建筑外壳、入口、楼梯与楼层生成
  → 材料目录、门面模板与可选 AI 设计
  → 空间 / 通达 / 材料检查与预览
  → 导出 → 游戏导入 → 实际行走与保存验收
```

架构按数据、规划、生成、游戏适配分层，通过版本化文件交换结果。
道路几何、建筑方块和交通运行对象必须分开，不能把轨道外观当成已运行线路。
阶段产物需要可检查、可复现；后续支持局部重新生成，避免每次改门面都重建整城。
当前尚未完成全链路增量构建或统一调度器。

## 5. AI 使用规则

AI 负责风格、配色、门面模块组合、材料选择建议和预览审美检查。
确定性程序负责坐标、几何、碰撞约束、合法状态、方块导出与结果校验。

计划支持两种输入方式，共用结构化设计协议：

1. 工作区方式：由 GPT 等生成设计文件，生成器读取并校验。
2. 在线 API 方式：生成器按需调用模型，返回同样的设计结构。

不绑定单一服务商，不要求用户现在提供密钥；没有 API 时基础规则生成仍可运行。
AI 不得编造材料 ID、MTR API 或真实地理事实，不直接获得世界写入权限。
在线模型应按需调用、缓存结果并设置费用上限；未实现前不得声称已有这些控制。
AI 设计文件到实际方块的完整连接目前尚未实现。

## 6. 材料与模组兼容

采用语义材料目录和版本化适配器，不把“安装了模组”等同于“完全自动理解”。

| 层级 | 内容 | 验证方式 |
| --- | --- | --- |
| 普通材料 | 墙面、玻璃、静态装饰 | ID、状态、实际注册与渲染检查 |
| 复杂装饰 | 文字招牌、连接模型、位移与组合模型 | 附加数据、邻接更新、碰撞与保存测试 |
| 功能系统 | MTR、飞机、机械设备 | 独立功能适配、操作与持久化测试 |

Yuushya 是第一批重点适配材料。可从官方公开包和源码开始整理，不要求用户先提供整合包；
后续核对 Windows 实际版本、依赖与运行结果。
材料目录记录版本、身份、名称、视觉用途、状态、特殊数据、验证程度及降级方式。
资源静态扫描仅提供候选目录，不等于运行时注册表或所有状态的有效性证明。
未知材料不得静默替换；允许明确记录的原版降级。
代码、美术素材、地图数据按各自许可处理，默认不随本仓库再分发第三方 JAR 和素材。

## 7. 交通与扩展范围

真实街区是近期验收主线，同时验证 MTR 技术可行性。
MTR 建立独立“两站一线”对照：能配置、能从 A 乘到 B、能保存并重启恢复，
区分手工配置和程序自动创建；精确版本源码与游戏证据齐备后才实施写入适配器。
分岔、合流、交叉与信号控制在基础闭环之后验证。
如果自动化路径未证实，明确保留手工方案，不假称已经自动联动。

交通验证不阻塞静态城市生成。地图导航优先使用现有模组，飞机是后续可选扩展；
不把飞行、自动驾驶、机场运行或完整铁路时刻表纳入近期必交范围。

## 8. 阶段交付与验收

### A / M2：真实街区生成闭环（当前主线）

从池袋东口方向的 Sunshine 60 通局部样板开始。
验收：布局有真实来源；成功导入；道路、入口、楼梯和开放上层实际可走；
简化与推定明确；保存退出重进正常。完整地标尚不包含在当前样板中。

### B：Yuushya 门面与材料

建立匹配版本的候选目录和首批材料映射，验证朝向、渲染、碰撞、连接效果与保存。
先静态材料，再复杂装饰；材料整理可以与阶段 A 的 Windows 验收并行。

### C：地标、完整街区与选择性压缩

扩大范围，补齐重要地标、复合轮廓、窄楼与高程问题。
压缩普通街段，对照未压缩样板验收失真、地标相对位置和通行质量。

### 并行 M3：MTR 两站一线

先证明实际运行闭环，再决定自动化深度；不把该项列为已完成。

### 后续：产品化与扩展

Windows 安装与操作界面、分区增量生成、更多城市和材料包，以及经验证的功能模组适配。
每阶段先完成一个可验收闭环，不设未经测量的整城规模和工期承诺。

## 10. 工程底线与成功标准

1. 先验证版本、许可、格式和能力，后依赖；不编造 API、测试结果或兼容性。
2. 固定输入、版本与 seed 时结果可复现，记录来源、参数、摘要、推定、遗漏和失败原因。
3. 不未经确认覆盖玩家世界；当前使用独立测试世界。未来直接写入必须有预览、备份、区域限制和可验证撤销。
4. 不用离线检查、编译成功或预览图替代游戏内验收；精确碰撞、保存和功能系统以实测为准。
5. 明确区分已完成、部分完成、待验证与计划，不把路线图当现有功能。
6. 不为了使用 AI 而让模型承担确定性计算；不以装饰复杂度牺牲可探索性。
7. 不随意复制第三方项目或素材；发布前检查依赖许可、数据署名和分发边界。
8. 保留用户修改和历史产物；每轮围绕可验收结果推进，不无依据扩大范围。

成功标准：指定真实地点后，生成一片位置关系可信、街景协调、建筑可探索的 Minecraft 城区；
随着适配成熟，再连接成可乘车游览的世界。质量与可用性优先于建筑数量。
